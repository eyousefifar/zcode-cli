**2. Missing risks in the fork-and-own plan**

- **Existing fork output silently becomes authoritative.** The latest build script rebuilds the fork only when `packages/tui/dist/index.js` is absent. Source edits can therefore produce a successful release containing stale UI code. It also selects any available fork immediately, contrary to the documented rule that vendor remains active until parity passes. See [scripts/build.sh:16](/Users/erfanyousefifar/Codes/zcode-cli/scripts/build.sh:16) and [PARITY.md:7](/Users/erfanyousefifar/Codes/zcode-cli/docs/tui/PARITY.md:7).

- **The overlay is mutable build state without provenance verification.** Directly invoking `build.ts` bypasses overlay preparation; reinstalling dependencies can replace it; release fallback can silently select vendor or stub. Additionally, `bun install --frozen-lockfile || bun install` abandons reproducibility when the frozen installation fails. Require an explicit implementation selection, rebuild it, and record the source revision and overlay hash. See [scripts/build.sh:15](/Users/erfanyousefifar/Codes/zcode-cli/scripts/build.sh:15) and [build.ts:37](/Users/erfanyousefifar/Codes/zcode-cli/build.ts:37).

- **“External pi-tui” needs a precise two-stage definition.** It is external to the TUI artifact, but should be bundled into the final executable. Accidentally preserving that external boundary in the final build would require an installed package at runtime; currently pi-tui is only a root dev dependency. The root pins `0.85.1`, while the fork manifest allows `^0.85.1`. Record which resolved version is tested and shipped. See [package.json:38](/Users/erfanyousefifar/Codes/zcode-cli/package.json:38), [packages/tui/package.json:9](/Users/erfanyousefifar/Codes/zcode-cli/packages/tui/package.json:9), and [vendor/zcode-tui-index.js:8](/Users/erfanyousefifar/Codes/zcode-cli/vendor/zcode-tui-index.js:8).

- **Native-addon support does not imply automatic embedding.** pi-tui constructs addon paths and calls `createRequire()` dynamically, searching installed-package and executable-adjacent locations. The final build contains no explicit addon packaging step. Missing helpers can silently degrade keyboard behavior, including Apple Terminal Shift+Enter. Bun documents direct addon references for reliable embedding; this specific loader needs verification in a directory without the checkout or `node_modules`. See [native-module-path.js:6](/Users/erfanyousefifar/Codes/zcode-cli/node_modules/@earendil-works/pi-tui/dist/native-module-path.js:6), [native-modifiers.js:29](/Users/erfanyousefifar/Codes/zcode-cli/node_modules/@earendil-works/pi-tui/dist/native-modifiers.js:29), and [Bun’s addon guidance](https://bun.com/docs/bundler/executables#embed-n-api-addons).

- **Cross-compilation configuration needs correction or explicit validation.** `build.ts` puts platform triples in top-level `target`, suppressing typing with `as never`; Bun documents platform selection under `compile.target`. CI also installs `latest` Bun, making behavior drift harder to diagnose. Compile success and a Linux `--version` check do not establish interactive behavior on four targets. See [build.ts:43](/Users/erfanyousefifar/Codes/zcode-cli/build.ts:43), [.github/workflows/release.yml:17](/Users/erfanyousefifar/Codes/zcode-cli/.github/workflows/release.yml:17), and [Bun’s cross-compilation API](https://bun.com/docs/bundler/executables#cross-compile-to-other-platforms).

- **The ownership boundary extends beyond TUI source.** The bundle includes model-access/preflight/configuration helpers and an app-server client. The new provenance file acknowledges copied CLI helpers, but the architecture does not explain responsibility for keeping these aligned with the core. Login self-spawning and plugin-reference fallback also depend on launcher paths and `process.argv`, which differ between npm and compiled execution. An environment-injected login stub would bypass that risk. See [packages/tui/PROVENANCE.md:5](/Users/erfanyousefifar/Codes/zcode-cli/packages/tui/PROVENANCE.md:5), [vendor/zcode-tui-index.js:161811](/Users/erfanyousefifar/Codes/zcode-cli/vendor/zcode-tui-index.js:161811), and [vendor/zcode-tui-index.js:165855](/Users/erfanyousefifar/Codes/zcode-cli/vendor/zcode-tui-index.js:165855).

**3. Weaknesses in the testing plan and query responder**

- **Tier 2 needs a production injection point first.** `ZCodeTui` directly constructs `NotifyingProcessTerminal`; `run()` checks global `process.stdin/stdout.isTTY`. Declared stream options do not redirect its main renderer, and `ZCodeTui` is not exported by the vendor bundle. A `VirtualTerminal` alone cannot drive the proposed whole-app tests. Add a small terminal factory seam and route lifecycle checks through it. See [vendor/zcode-tui-index.js:166166](/Users/erfanyousefifar/Codes/zcode-cli/vendor/zcode-tui-index.js:166166), [vendor/zcode-tui-index.js:166292](/Users/erfanyousefifar/Codes/zcode-cli/vendor/zcode-tui-index.js:166292), and [vendor/zcode-tui-index.js:170421](/Users/erfanyousefifar/Codes/zcode-cli/vendor/zcode-tui-index.js:170421).

- **The responder table contains two concrete protocol mistakes.**
  - DSR `CSI ? 997 ; 1 n` means **dark**; `…;2n` means **light**. The table reverses them. I verified this against the installed parser.
  - pi-tui emits OSC 11 terminated by **BEL**, while the table lists only **ST**. An exact-match implementation would miss the actual query.

  See [TESTING.md:29](/Users/erfanyousefifar/Codes/zcode-cli/docs/tui/TESTING.md:29), [terminal-colors.js:52](/Users/erfanyousefifar/Codes/zcode-cli/node_modules/@earendil-works/pi-tui/dist/terminal-colors.js:52), and [tui.js:1007](/Users/erfanyousefifar/Codes/zcode-cli/node_modules/@earendil-works/pi-tui/dist/tui.js:1007).

- **Keyboard negotiation is not merely “no Kitty reply → timeout.”** pi-tui sends a combined enable/query/DA sequence; DA without Kitty confirmation activates `modifyOtherKeys`. Test supported Kitty, DA fallback, silence, fragmented responses, and late responses separately. Otherwise modified-key regressions remain invisible. See [terminal.js:168](/Users/erfanyousefifar/Codes/zcode-cli/node_modules/@earendil-works/pi-tui/dist/terminal.js:168).

- **PTY response handling is feasible and belongs in Tier 3 too.** The harness already receives output and writes input through `Bun.Terminal`. `@xterm/headless` itself emits a DA response through `onData`—confirmed by a probe—but `TerminalScreen` never forwards it. Share response plumbing across tiers, avoid duplicate built-in/custom responses, and handle split/coalesced sequences. Test OSC-only, DSR-only, contradictory responses, timeout, `COLORFGBG`, explicit themes, and `NO_COLOR`. See [terminal-screen.ts:24](/Users/erfanyousefifar/Codes/zcode-cli/test/helpers/terminal-screen.ts:24) and [tui-session.ts:30](/Users/erfanyousefifar/Codes/zcode-cli/test/helpers/tui-session.ts:30).

- **Current assertions can pass without the advertised behavior.** `/help` can match its echoed command; `/status` accepts generic words; neither asserts panel closure. The mock concatenates all SSE chunks into one response body, so observing its sentinel does not prove incremental rendering, cancellation responsiveness, or redraw coalescing. Use unique panel content, before/after assertions, and controllably paced streams. See [test/tui.e2e.test.ts:68](/Users/erfanyousefifar/Codes/zcode-cli/test/tui.e2e.test.ts:68) and [model-server.ts:63](/Users/erfanyousefifar/Codes/zcode-cli/test/helpers/model-server.ts:63).

- **The suite is not self-contained.** It copies real encrypted credentials and selects an account provider. A clean CI machine cannot reproduce that fixture, and there is no demonstrated network-denial boundary. Separately, the supposedly offline gate always runs `perf.sh`, which makes real authenticated API calls regardless of `RUN_ONLINE`. See [sandbox.ts:106](/Users/erfanyousefifar/Codes/zcode-cli/test/helpers/sandbox.ts:106), [test/tui.e2e.test.ts:14](/Users/erfanyousefifar/Codes/zcode-cli/test/tui.e2e.test.ts:14), and [scripts/perf.sh:30](/Users/erfanyousefifar/Codes/zcode-cli/scripts/perf.sh:30).

- **Text snapshots cannot establish visual parity.** `snapshot()` omits cell attributes and trims trailing whitespace/empty lines. A probe produced identical snapshots for red and green text. The planned serializer must preserve cell widths, colors, inverse styling, cursor state, and both buffers; resizing requires a size-event history, not replaying bytes at one final size. PNG reconstruction also cannot establish Kitty/iTerm image rendering or flicker behavior. See [terminal-screen.ts:50](/Users/erfanyousefifar/Codes/zcode-cli/test/helpers/terminal-screen.ts:50) and [TESTING.md:59](/Users/erfanyousefifar/Codes/zcode-cli/docs/tui/TESTING.md:59).

- **Harness lifecycle and performance coverage are incomplete.** Startup failure leaks the session before callers can clean it up; `close()` has no bounded termination fallback or explicit PTY closure; `screenHistory()` returns current screen lines, not history. No session resize API exists. The performance script measures `--version` and headless turns, not the documented keystroke/render budgets. See [tui-session.ts:65](/Users/erfanyousefifar/Codes/zcode-cli/test/helpers/tui-session.ts:65), [tui-session.ts:93](/Users/erfanyousefifar/Codes/zcode-cli/test/helpers/tui-session.ts:93), and [scripts/perf.sh:18](/Users/erfanyousefifar/Codes/zcode-cli/scripts/perf.sh:18).

**5. Top five recommendations, ranked**

1. **Make fork selection and release builds deterministic.** Rebuild source every time; fail frozen installs; prohibit implicit release fallback; record core/fork/pi-tui/Bun versions and artifact hashes. Run the actual acceptance gate from the release workflow.
2. **Repair the existing E2E foundation before expanding it.** Fix the helper signature, add type checking, replace machine credentials with reproducible fixtures, enforce offline traffic, strengthen panel assertions, and make cleanup bounded.
3. **Validate standalone packaging independently.** Correct cross-target configuration; exercise native modifier handling, login self-spawn, and plugin fallback outside the checkout on supported targets. Include npm interactive smoke coverage.
4. **Add one terminal injection seam and a shared, tested responder.** Correct DSR values and OSC terminators; cover supported, unsupported, fragmented, and delayed negotiation in both in-process and PTY tests.
5. **Turn parity into an evidence-backed release checklist.** Prioritize permissions, input delivery, rewind, secrets, and terminal recovery; retain vendor-versus-fork captures for identical scenarios. Supplement text assertions with cell attributes and selected real-terminal visual checks.
